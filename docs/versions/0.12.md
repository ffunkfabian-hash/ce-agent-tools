# Agent Tools 0.12 – Gatehouse

Abnahme: **311 Tests und Quick grün**, unabhängiger Opus-5.5-high-Richter mit Freigabe. Native Projekt-/Workspace-Proben am Mac am 22.10.2026. Globaler Einbau und tatsächlicher Rolloutstatus stehen in der [PR-Beschreibung](https://github.com/ffunkfabian-hash/ce-agent-tools/pull/10).

## Verhalten

Codex und Antigravity erhalten dünne Adapter vor derselben Entscheidung `guard.decide` und denselben Regeldateien wie Claude Code. Es gibt keine zweite Regelimplementierung. Codex verwendet `Bash`/`apply_patch`; Antigravity wird anhand der gemessenen Argumente `CommandLine`, `Cwd`, `TargetFile`, `CodeContent` und Ersatz-Blöcken übersetzt. Claude behält seine Session-/Stop-Hooks.

Ein schlichtes `git commit` auf main ging vorher durch, weil die alte Regel nur einen Branchwechsel im Befehlstext erkannte. Das Regelfeld `git_commit` liest jetzt bei **einem einzelnen einfachen Git-Commit aus festen Wörtern** den tatsächlichen Branch: Client-Ordner, `git -C`, `--git-dir`, `--work-tree`, `--bare` und geerbte Repo-Variablen. Zitate, Backslashes und Kommentare werden berücksichtigt. Die vollständige Referenz `refs/heads/...` vermeidet Verwechslungen mit gleichnamigen Tags; nur die exakt geschriebenen Branches `main` und `master` sind geschützt, `MAIN`/`Master` bleiben Arbeitsbranches.

Die Vorabprüfung simuliert keine Shell. Präfix-Zuweisungen (`GIT_DIR=...`, `CE_ALLOW_MAIN=1`), Operatoren, Variablen, Funktionen, Pipelines, Subshells, Heredocs, Umleitungen und unbekannte Git-Optionen werden mit Hinweis dem Git-Netz überlassen. Skriptdateien und Aliase werden nicht aufgelöst. Ohne installiertes Git-Netz besteht für diese Formen keine technische Commit-Sperre. Die vorhandene Regel gegen `--allow-empty-message` bleibt für sicher erkannte Git-Commit-Abschnitte bestehen.

Branch-Abfragen starten ausschließlich ein festes System-Git mit kleiner Umgebung, niemals ein `git`, einen Loader oder `PATH` aus der geprüften Zeile. Ein Fehler oder eine Delegation in dieser Vorabprüfung lässt die übrigen Regeln weiterlaufen: etwa `heavy-resource`, Force-Push und nacktes Stash bleiben unabhängig wirksam.

## Git-Netz

`githooks/ce_githooks.py install|uninstall|status --repo <Pfad> [--dry-run]` richtet einen reversiblen lokalen `core.hooksPath` im gemeinsamen Git-Ordner ein:

- `pre-commit`: Commit auf `main`/`master` gesperrt.
- `pre-push`: Updates/Anlegen von `main`/`master`, Löschen geschützter Branches, Überschreiben vorhandener Tags und echte Nicht-Fast-Forwards gesperrt.
- `CE_ALLOW_MAIN=1` erlaubt dem Nutzer ausdrücklich Commit/Push nach main/master; es erlaubt kein Überschreiben fremder Historie oder Löschen geschützter Branches. Die Ausnahme gilt im Git-Netz, nicht als Ausnahme des einfachen Client-Commits.
- Vorhandene Hooks werden erhalten und mit denselben Argumenten, derselben Eingabe und ihrem Exitcode weitergerufen. Andere schon vorhandene Git-Hooks erhalten Weiterleitungen. Rückbau stellt den vorherigen lokalen `core.hooksPath` wieder her.

Grenzen: `--no-verify` und ein eigener `-c core.hooksPath=...` umgehen das Netz. `pre-push` sieht Referenzen statt Optionen: ein Push mit `--force`, der tatsächlich ein Fast-Forward ist, ist dort nicht unterscheidbar (die vorhandene Client-Regel prüft die Optionen). Merge-Commits verwenden `pre-merge-commit` und sind von diesen beiden neuen Schranken nicht erfasst. Das Netz ist keine lückenlose Sicherheitsgrenze.

## Fehler und Einbau

Adapter liefern bei internen Fehlern Exit 0 und eine Meldung im jeweiligen Clientformat. Auch nicht ladende Module werden abgefangen. Nexogens erzeugter Shell-Befehl fängt fehlende Skripte/Python sowie Syntax-/Importfehler des Einstiegs ab; Exit 2 würde Codex sonst als allgemeine Sperre werten. Der Git-Wrapper behandelt nur den eigenen Ablehnungscode 86 als Sperre, alle Startfehler gehen mit Meldung an den bisherigen Hook weiter.

Nexogens optionaler Installer ergänzt `~/.codex/hooks.json` und `~/.gemini/config/hooks.json` mit nummerierter Sicherung, Vorschau und Besitz-/Konfliktprüfung; bestehende Hooks und MCP-Server bleiben erhalten. Codex muss neue oder geänderte Definitionen regulär unter `/hooks` prüfen und vertrauen. Antigravitys Hook-`allow` belässt die normale Terminalfreigabe; es verwendet kein `auto_approve`.

```sh
./install.sh --rules-only --client-hooks --git-hooks --dry-run
./install.sh --rules-only --client-hooks --git-hooks
./install.sh --remove-hooks --dry-run
```

Dauerhafte Quelle ist der Haupt-Checkout von Agent Tools. Der Git-Einbau lässt `repos.json`-Einträge mit `hold` aus, auch über Alias oder Worktree desselben Git-Ordners. Toolgen/Lockstep wird weder synchronisiert noch an seiner Sitzung abgefragt. Die fünf übrigen Fachrepos erhalten die geprüften eingebetteten Werkzeugkopien per `ce_sync.py` nach dem Tools-Merge.

Befehle und tatsächliche Ausgaben:

- `git commit -m 'Gatehouse bounded native main probe'` → `Command blocked by PreToolUse hook: [commit-on-main]` (Codex) bzw. `tool call denied by pre-tool hook` (Antigravity); keine neue main-Revision.
- `git commit -m 'Gatehouse bounded native working probe'` → die drei oben genannten Commits.
- `python3 .../heavy_lock.py run -- true` → `[heavy-resource]`; kein schwerer Prozess. Codex sendete bei dieser Probe zusätzlich ein abschließendes `.` als Argument; auch diese tatsächliche Zeile wurde vor der Ausführung gesperrt.
- `bash .agents/skills/ce-testing/scripts/verify.sh run --full` → ausschließlich `STUB_VERIFY_ONLY`, Exit 0. Der Stub enthält nur printf/Marker. Codex zeigte `[heavy-unlocked]`. Antigravity emittierte den Text in `allow.reason`, zeigte ihn dem Agenten jedoch nicht sichtbar an.
- `printf 'BOUNDED_<CLIENT>_FAULT_ALLOWED\n'` bei absichtlich ungültiger `guard.py` nur in `bounded-fault-plugin/` → Ausgabe und Exit 0. Der Fehlertext steht im Hook-Ergebnis (`systemMessage` bzw. `allow.reason`), war dem Agenten in diesen Proben nicht sichtbar. Produktionsdateien wurden nicht beschädigt.

Die endgültige Aufteilung wurde anschließend in allen drei geforderten Clients mit installiertem Git-Netz gemessen:

```sh
target=main; git switch "$target" && git commit --allow-empty -m 'Gatehouse net main probe'
target=codex/gatehouse-probe; git switch "$target" && git commit --allow-empty -m 'Gatehouse net working probe'
```

Die Client-Vorabprüfung ließ beide Zeilen mit Git-Netz-Hinweis durch. Der erste Aufruf endete am tatsächlichen `ce-shared pre-commit: abgelehnt` (Exit 1), die drei main-Referenzen blieben unverändert. Der zweite erzeugte Arbeitsbranch-Commits: Codex `b622002`, Antigravity CLI `79ac876`, IDE `0048d82`. Antigravity verwendete normale Einzelfreigaben. Belege: `bounded-codex-net.jsonl`, normale Hook-Ereignisprotokolle, CLI-Terminalprotokoll und `bounded-net-git-state.json`.

Zusätzlich gemessen: Codex `apply_patch` und IDE `write_to_file` erzeugen eine lokale Workflow-Probedatei. `[actions-sparsam]` ist in Codex sichtbar, in Antigravity nur im Hook-Ergebnis. Die IDE lädt Workspace-Hooks trotz fehlendem Hooks-Reiter; der historische IDE-2.0-Forenbefund trifft auf IDE 2.5.5 nicht zu.

Nur Einordner-Workspaces sind gemessen. CLI 1.4.5 sendet kein `Cwd`; der Adapter nimmt den ersten `workspacePaths`-Eintrag. Bei mehreren Ordnern kann das der falsche Repo-Kontext sein (falsche Vorabsperre oder Durchlass); dort einen einzelnen Workspace bzw. einen ausdrücklichen absoluten `git -C`-Kontext verwenden. Das Git-Netz prüft unabhängig davon den tatsächlichen Git-Aufruf. Weitere Dateiwerkzeuge, Antigravity App und Codex Desktop sind nicht als abgenommen ausgewiesen.
