## Client-Adapter

`guard.decide(payload)` bleibt die einzige Entscheidung; Claude Code ist unverändert. `client_adapter.py` wandelt die
Clienteingabe in Claude-förmige Payloads, lässt jede mit den Regeln des Plugins entscheiden und fasst zusammen (Blocks
vor Warnungen, jede Meldung einmal). Claude-Subagent-Profile werden nicht übertragen: Codex meldet `agent_type` für eigene
Agenten, ein gleichnamiges Claude-Profil darf dort nicht greifen.

Quellen vor der Umsetzung: Codex-Hooks-Doku (`developers.openai.com/codex/hooks` → `learn.chatgpt.com/docs/hooks`) und die
generierten Schemas `codex-rs/hooks/schema/generated` am Tag `rust-v0.162.1` (installiert: codex-cli 0.162.1; Kopie in
`tests/fixtures/codex-hooks-0.162.1`). Antigravity: `antigravity.google/docs/hooks?tab=ide` (Weiterleitung von
`/docs/ide/hooks`) sowie die im installierten `Antigravity.app` 2.25.0 (`Contents/Resources/bin/language_server`)
eingebettete Hook-Doku.

| | Codex | Antigravity |
|---|---|---|
| Ort | `~/.codex/hooks.json` (User-Ebene; Projekt-Hooks nur in vertrauten Projekten) | `~/.gemini/config/hooks.json` (global), `.agents/hooks.json` (Workspace) |
| Aktiv erst | nach Vertrauen des genauen Eintrags unter `/hooks` (Hash; jede Änderung braucht neues Vertrauen) | laut Doku sofort (`enabled`), Verwaltung unter „… > Customizations > Hooks“ |

Abweichungen, die nur eine echte Messung klärt: Die Web-Doku beschreibt `allow` als „an Folgehook oder normale Freigabe
weiterreichen“ (daneben `auto_approve`), die eingebettete Doku als „automatisch erlauben“; der installierte Stand kennt
`auto_approve`, also vermutlich die Web-Semantik. Werkzeugnamen leitet der Language-Server aus Step-Typen ab
(`CORTEX_STEP_TYPE_*`, etwa `CODE_ACTION`, `SHELL_EXEC`, `MCP_TOOL`); der Adapter urteilt deshalb nach Argumentform, der
Matcher bleibt bei den dokumentierten Namen, bis die Messung andere zeigt. Hooks laufen im Ordner der `hooks.json`, nicht
im Workspace. Exitcode-, Zeitlimit- und JSON-Fehlerverhalten sind nicht dokumentiert. Antigravity CLI `agy` 1.4.5
und die eigenständige IDE 2.5.5 sind gemessen und werden getrennt ausgewiesen (Tabelle unten); die Antigravity App 2.25.0
ist nicht gemessen.

Der eingetragene Befehl prüft Skript und Python vor dem Start: `python3 fehlt.py` endete sonst mit Exit 2, was Codex als
Sperre jedes Werkzeugaufrufs liest. Auch ein Startfehler des vorhandenen Skripts muss eine Meldung ohne Block ergeben. Die Git-Wrapper unterscheiden
dafür den eigenen Ablehnungsstatus (`REJECT` = 86 von `check`) von Startfehlern und reichen anschließend an den vorherigen
Hook weiter; dessen Exitcode und Eingaben bleiben erhalten (die Weiterleitung macht der sh-Wrapper, nicht Python). Der
Nexogen-Befehl reicht nur eine Adapterantwort mit Exit 0 durch, sonst „guard startet nicht“ ohne Block; die Adapter
selbst antworten auch dann offen, wenn `guard.py` nicht lädt.

## commit-on-main nach dem tatsächlichen Branch

Die erste echte Codex-Probe des Koordinators (codex exec 0.162.1, vertrauter Projekt-Hook, `CE_HOOK_LOG`) zeigte: Der Adapter
wurde aufgerufen, ein schlichtes `git commit` in einem Wegwerf-Repo auf main lief trotzdem durch. Ursache war die bestehende
Regel selbst – sie erkannte nur den Text `checkout main && … commit`; Claude Code hatte dieselbe Lücke. Korrigiert in
`guard.py`, nicht in den Adaptern: das Regelfeld `git_commit` bestimmt für jeden echten `git commit`-Aufruf den Branch aus
dem Sitzungsordner, `cd`, `git -C` und einem vorherigen `checkout`/`switch` derselben Zeile (Pfad-Checkout mit `--` oder
Datei ändert ihn nicht). Unbekannter oder losgelöster HEAD sperrt nicht. Die gemessene Eingabe liegt als Fixture vor und
wird auf main abgelehnt, auf einem Arbeitsbranch nicht. Die Nachprüfung unterscheidet Datei-Checkout und Branchwechsel,
`switch main --`, Verzeichniszustand in Subshells, echte Heredocs und Text sowie `--git-dir`/`--work-tree`/`GIT_DIR`.
Auch eingebettete Shellbefehle und Substitutionen werden gelesen. Externe Skriptdateien und erst zur Laufzeit bekannte
Pfade bleiben außerhalb der statischen Prüfung; dafür dient das Git-Netz.

## Git-Netz

`githooks/ce_githooks.py` – Regeln und Grenzen im [README](../../README.md#git-netz). Gewählt ist ein eigener lokaler
`core.hooksPath` (`<git-common-dir>/ce-hooks`) statt Dateien in `.git/hooks` zu ersetzen: kein vorhandener Hook wird
verschoben, ein globaler oder versionierter Hook-Ordner (z. B. `.husky`) bleibt unberührt, und Rückbau ist ein
Konfigurationswert. Weitergereicht werden nur Hooks, die beim Installieren im vorherigen Ordner liegen; bloße Präsenz von
`push-to-checkout` oder `proc-receive` ändert Gits Verhalten, Platzhalter für alle Namen wären falsch. `status` meldet
später hinzugekommene Hooks.

## Prüfstopp nach dritter unabhängiger Prüfung

Die vorherigen Korrekturen sind nachvollziehbar; der zusätzliche statische Shell-Leser bleibt unvollständig. Offen:

| Schwere | Gegenfall | Fehler |
|---|---|---|
| hoch | `target=main; git switch "$target" && git commit -m x` | Nicht exportierter, statisch bekannter Variablenwert wird ignoriert. |
| hoch | `save() { git commit -m x; }; GIT_DIR=/main/.git save` | Temporäre Zuweisung erreicht den Funktionsaufruf nicht. |
| hoch | Verzögerter Branchwechsel in einer parallelen Pipeline | Parallele Pipeline wird nur in einer Reihenfolge betrachtet. |
| hoch | `git switch -c fix missing-start; git commit -m x` | Erkennbarer Wechsel-Fehler kann main weiter ausschließen. |
| niedrig | `bash -c 'exit 0; git commit -m x'` | Unerreichbarer Commit wird fälschlich gesperrt. |

Beleg: `/Users/ffunk/Library/Caches/CubeEscape/hook-client-20261022/tools-judge-final.txt`.
