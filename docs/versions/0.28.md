## Anlass

`~/.vibe/hooks.toml` zeigte: Vibe 3.0.4 committet als `cd <absoluter Pfad> && git commit --allow-empty -m probe-on-main`.
Die Vorabprüfung beurteilte seit Gatehouse (0.12) nur einen einzelnen einfachen `git … commit` und gab die Zeile mit
Hinweis an das Git-Netz; im Probe-Repo ohne Netz landete `074a5e7 probe-on-main` auf `main`
(`~/Library/Caches/CubeEscape/vibe-guard-20261030/probe-installed-home-*`).

## Umsetzung

- `guard.py` › `shell_segments` liefert alle Konstrukte der Zeile in Reihenfolge statt nur des ersten (Aufrufer nehmen das
  erste wie bisher als Grund im Hinweis).
- Neu `cd_target(words, cwd)`: Ziel eines Abschnitts aus genau `cd` (eingebaut, wörtlich) und einem festen Pfad; keine
  Option, kein `-`/`+N`, kein leerer Pfad; ein bloßer relativer Name nur, solange `CDPATH` im Hook-Prozess leer ist (cd
  sucht dort zuerst). Das Ziel zählt nur, wenn jede Shell dort landet: logisch Teil für Teil gebildet, jedes `..` nur hinter
  einem vorhandenen Ordner (bash und zsh lassen `fehlt/..` und `datei/..` scheitern), Ziel vorhanden (sonst versuchen beide
  den physischen Pfad) und logischer Pfad = physischer (`realpath`), damit `cd -L`, `cd -P`, `set -P` und zsh
  `chase_dots`/`chase_links` übereinstimmen.
- `commit_facts` beurteilt zusätzlich: Konstrukte genau `[Operator &&]`, zwei Abschnitte, der zweite ein fester
  `git … commit` (`commit_call` wie bisher) → Branch per `read_branch(Ziel, git-Kontext)`, also auch `git -C` relativ zum
  Ziel und geerbtes `GIT_DIR`. Erfüllt das Ziel die Bedingungen nicht, geht die Zeile mit Hinweis an das Netz.
- Alles andere bleibt unverändert beim Git-Netz: `;`, `||`, `&`, mehrere `&&`, Zeilenumbruch, Subshell, Variablen,
  `cd -P`, `cd` ohne/mit zwei Argumenten, `/usr/bin/cd`, `builtin cd`, `pushd`, Präfix-Zuweisung oder Wrapper vor `git`.

### Warum das keine Shell-Nachbildung ist

Gatehouse hat einen Leser zurückgebaut, der Ablauf und Zustand der Shell simulierte (Branchwechsel, Funktionen, Variablen,
Exitcodes). Gangway bleibt bei der statischen Lesart: dieselbe Wortzerlegung wie bisher, ein festes Muster aus zwei
Abschnitten, keine Ablaufsteuerung, kein Zustand außer dem Zielordner, den das eingebaute `cd` deterministisch aus festem
Text bildet. Die Grenzfälle der `cd`-Semantik (`CDPATH`, `-L`/`-P`, `..` über Links oder fehlende Ordner, physischer
Rückfall, `cd -`, Verzeichnisstapel) werden nicht nachgebildet, sondern ausgeschlossen: Beurteilt wird nur, wo alle
Lesarten denselben Ordner ergeben. Die übrigen Zeilen gehen mit Hinweis an das Netz wie zuvor. Der Laufzeittest mit echter
bash und zsh belegt beides, gesperrte und ans Netz gegebene Zeilen.

## Grenzen

- Ist `cd` in der Shell eine Funktion oder ein Alias (z. B. zoxide) oder setzt erst eine Startdatei der Shell `CDPATH`,
  kann das echte Ziel abweichen. Eine falsche Sperre bräuchte einen vorhandenen Ordner auf `main` unter dem gelesenen
  Pfad, während die Shell woandershin wechselt; der Ausweg ist dann ein einzelner `git -C <Pfad> commit`.
- Pfade mit führendem `..` setzen voraus, dass `cwd` der Hook-Eingabe dem logischen `$PWD` der Shell entspricht – dieselbe
  Annahme wie seit 0.12 für den einfachen `git commit`.
- `cd X && git log --grep commit` bekommt wie bisher einen Hinweis (Texterkennung), keine Sperre.
