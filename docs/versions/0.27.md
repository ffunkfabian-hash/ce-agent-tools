## Gemessenes Hook-Format (Vibe 3.0.4)

Quelle: die mit Vibe ausgelieferte Doku (`vibe/plugins/builtins/vibe/skills/vibe/SKILL.md` › Hooks), `vibe/core/hooks/`
und zwei Log-Hooks in Wegwerf-Repos (`vibe --trust --auto-approve -p`).

- Konfiguration: `[[hooks]]` in `<projekt>/.vibe/hooks.toml` (nur vertrauter Ordner) und `$VIBE_HOME/hooks.toml`
  (Standard `~/.vibe`); Felder `name`, `type` (`pre_tool`/`post_tool`/`post_agent`), `command` (Shellzeile in `/bin/sh`, im
  Sitzungsordner), `match` (fnmatch oder `re:`-Vollabgleich auf Kurz- oder qualifizierten Namen), `timeout` (60 s), `strict`.
- Eingang (stdin): `hook_event_name`, `session_id`, `parent_session_id` (gesetzt in Subagenten), `transcript_path`, `cwd`,
  `tool_name` immer qualifiziert, `tool_call_id`, `tool_input`. Gemessen: `file_system.bash` `{timeout, command}`,
  `process.start` `{command}` (Hintergrund; `match = "bash"` trifft ihn nicht), `file_system.write_file`
  `{file_path, content}`, `file_system.edit` `{file_path, old_string, new_string}`, `file_system.read_file` `{file_path}`.
  `file_path` kam relativ (`notes.txt`). `post_tool` zusätzlich `tool_status`, `tool_output`, `tool_output_text`.
- Ausgang: Exit 0 + leer = durch; Exit 0 + JSON `{decision, reason, system_message, hook_specific_output}`; alles andere
  ist Vibes Fehlerpfad (offen mit Warnung, außer `strict`). `pre_tool`-`deny` sperrt vor dem Freigabe-Prompt, der `reason`
  geht als Werkzeugfehler an das Modell. Modellkontext gibt es nur bei `post_tool` (`additional_context`).

Fixture: `tests/fixtures/vibe/measured-3.0.4-tool-hooks.json` (Pfade ersetzt).

## Umsetzung

- `hooks/vibe_guard.py` (über `client_adapter.run`, Client `vibe`): Shell-Werkzeuge (`bash`, `git_bash`, `powershell`,
  `process.start`) → Bash, ein eigenes `cwd`-Argument gewinnt; `file_path` + `content` → Write, + `old_string`/`new_string`
  → Edit (Argumentform entscheidet, Pfad relativ zu `cwd`); `mcp_<server>.<tool>` → `mcp__<server>__<tool>` für
  `merge-nur-sightline`; sonst nichts. `pre_tool`: Sperre `deny`, Warnung `system_message`; `post_tool`: Warnungen (und eine
  Sperre, falls der `pre_tool`-Eintrag fehlte) als `additional_context`. Nie `strict`, nie Umschreiben von `tool_input`.
- `ce_vibe.py`: `run` bricht vor dem Worktree ab, wenn `$VIBE_HOME/hooks.toml` keinen `pre_tool`-Hook hat, der ein
  vorhandenes `vibe_guard.py` aufruft und mit `match` `bash` und `process_start` trifft (Vibes Matcher nachgebaut), und
  nach dem Anlegen, wenn das `.vibe/hooks.toml` des Worktrees einen Hook gleichen Namens hat (`--trust` lädt es, der
  Projekteintrag gewänne); `status` nennt `guard_hook` und die gelesene Datei.
- README › „Andere Clients“ (Tabellenzeile, Lücken), › Mistral Vibe („Wächter Pflicht“), › Erfahrungen; AGENTS.md.
- Eintrag in die Nutzerkonfiguration: Nexogens `./install.sh --client-hooks=vibe` (Patch-Branch
  `claude/nexogen-patch-vibe-guard-hook`: markierter Block in `~/.vibe/hooks.toml`, fremde Hooks bleiben, Rückbau mit

## Was es nicht kann

- Eingaben an eine laufende Shell (`process.write`, `git_bash_stdin`, `powershell_stdin`) und Connector-Werkzeuge sieht der Wächter nicht; ein Agent, der eine
  Shell startet und ihr Befehle zuschiebt, umgeht ihn. Das Git-Netz bleibt das Netz darunter.
- Warnungen vor dem Lauf erreichen das Modell nicht (nur die Oberfläche); erst `post_tool` hängt sie an.
- Die Vibe-Extension (VS Code) und Vibes ACP-Weg sind ungemessen; laut Doku lesen sie dieselben `hooks.toml`.
- Claude-Subagent-Profile (`.claude/agent-guard.json`) gelten nicht für Vibe-Subagenten.
